# feature-dev — TerminalNinja feature/fix orchestrator

You are orchestrating a feature or bugfix for the TerminalNinja library end-to-end. Follow the four phases below in order. Each phase has a dedicated file with the detailed checklist — read it when you enter that phase.

## Guiding principles

- **User checkpoints are mandatory**, not optional. Stop where the phase file says stop. The user reviews and corrects before you continue.
- **Parallelism is real**: when a phase says "in parallel", emit multiple `Task` tool calls in a single message. Do not serialize them.
- **Every feature ships with a sample.** Every fix updates the affected sample(s). Phase 4 refuses to open a PR without this.
- **Never skip the plan for a "small" change.** The plan is how the reviews and the user see your intent; skipping it removes their lever to correct you.
- **Respect `CLAUDE.md` and `AGENTS.md`.** They are the source of truth for patterns (DP, theming, MVVM, AOT constraints). Do not invent conventions.
- **Capture learnings.** When the user corrects you during Phase 3 checkpoints, write the correction to `learnings/<subject>/<slug>-task-N.md` with a `Why:` and `How to apply:` so future runs don't repeat it.
- **Commits and PR titles follow Versionize / Conventional Commits format.** The repo uses [Versionize](https://github.com/versionize/versionize) to compute semver bumps and generate the changelog from commit types. Deviation breaks the release pipeline — see the Commit format section below before committing.

## Commit format (Versionize / Conventional Commits)

Every commit and every PR title MUST follow this shape:

```
<type>(<optional-scope>): <imperative, lowercase summary>

<optional body — what and why, wrapped at 72 chars>

<optional footer — BREAKING CHANGE, refs, Co-Authored-By>
```

**Allowed types** (these drive Versionize's version bump):

| Type | Bump | When to use |
|------|------|-------------|
| `feat` | minor | new capability for library consumers |
| `fix` | patch | corrects a defect in existing behavior |
| `perf` | patch | measurable performance improvement with no behavior change |
| `refactor` | none | internal restructuring, no behavior change |
| `docs` | none | README, XML docs, `AGENTS.md`, `CLAUDE.md`, `docs/` |
| `test` | none | test-only changes |
| `build` | none | csproj, NuGet packaging, MSBuild targets |
| `ci` | none | GitHub Actions, workflows |
| `chore` | none | dependency bumps, housekeeping |
| `style` | none | formatting, whitespace only |

**Breaking changes**: append `!` after the type/scope AND add a `BREAKING CHANGE:` footer describing the migration. Example:

```
feat(databinding)!: rename BindingMode.Default to BindingMode.OneWay

BREAKING CHANGE: BindingMode.Default is removed. Replace with BindingMode.OneWay
which preserves the previous behavior for all built-in controls.
```

**Scopes** (use when the change is localized to one area — optional but preferred for clarity):

`button`, `checkbox`, `combobox`, `datagrid`, `listbox`, `tabcontrol`, `textbox`, `treeview`, `databinding`, `theming`, `xaml`, `aot`, `generators`, `layout`, `focus`, `input`, `dialogs`, `playground`, `sample`, `packaging`

The scope is the control or subsystem name, not the task number.

**Summary rules**:
- Imperative mood ("add", not "added" or "adds")
- Lowercase first word after the colon
- No trailing period
- Under 72 chars for the whole first line

**Examples from this repo's history** (good patterns):

- `feat: ListBox built-in scrolling — no ScrollViewer wrapper needed`
- `fix: focus visibility — add focus borders to list controls, fix ScrollViewer`
- `refactor: TabControl — clean underline design with half-block accent`
- `feat: auto-enable XAML hot reload when debugger is attached`

**Versionize-only commit** (do NOT produce these yourself — they're generated by `versionize run`):

- `chore(release): 0.2.0`

## Phase overview

1. **Phase 1 — Intake** → [phase-1-intake.md](phase-1-intake.md)
   Ask clarifying questions, decide `feature/` vs `fix/`, generate a slug, create the branch, seed `plans/<slug>/intake.md`.

2. **Phase 2 — Parallel reviews + plan** → [phase-2-reviews.md](phase-2-reviews.md)
   Launch three review subagents in parallel (NativeAOT, Security, Architecture). Synthesize into `plans/<slug>/plan.md`, broken into tasks. Stop for user approval.

3. **Phase 3 — Task execution loop** → [phase-3-tasks.md](phase-3-tasks.md)
   For each task: tests → implementation → five parallel reviews (XMLDocs, AOT, Security, Style, Unused) → fixes → user checkpoint → learnings → commit.

4. **Phase 4 — Finalize** → [phase-4-finalize.md](phase-4-finalize.md)
   Conformance check against intake, **mandatory sample gate**, update `docs/llms.txt` + `AGENTS.md` + `CLAUDE.md` if conventions changed, commit, open PR.

## Slug rules

- Lowercase, hyphen-separated, noun-first. Max 40 chars.
- Feature: `feature/<slug>` (e.g. `feature/slider-control`).
- Fix: `fix/<slug>` (e.g. `fix/textbox-selection-overflow`).
- Confirm the slug with the user in Phase 1 before creating the branch.

## Folder layout this skill maintains

```
plans/<slug>/
  intake.md         # Phase 1 output: user answers, acceptance criteria
  review-aot.md     # Phase 2 subagent output
  review-security.md
  review-arch.md
  plan.md           # Phase 2 synthesis, broken into tasks. User-approved.

learnings/<subject>/
  <slug>-task-N.md  # Phase 3 user-correction capture. Subject = control or subsystem name.
```

Both folders are committed to git as durable design history.

## When you are invoked

1. If the user gave you a short description as argument, treat it as the initial intent and open Phase 1.
2. If they gave no argument, ask: "What feature or fix do you want to work on?" then open Phase 1.
3. If an existing `plans/<slug>/` folder matches the user's current branch, resume from the latest phase (detect by which files exist).
